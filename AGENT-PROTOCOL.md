# Протокол взаимодействия агентов контура производства

Версия 1. Контракт между [poh-issue-agents](https://github.com/po-helper-org/poh-issue-agents),
[poh-pr-agents](https://github.com/po-helper-org/poh-pr-agents) и
[poh-pr-closer](https://github.com/po-helper-org/poh-pr-closer).

Агенты не вызывают друг друга. Они общаются через состояние GitHub — метки, ветки, комментарии,
события. Этот документ фиксирует, что именно является контрактом, кто чем владеет и какие правила
делают контур устойчивым.

---

## 1. Граница делегирования

Манифест организации проводит границу прямо: **техническая реализация и архитектура — за
человеком**. Контур производства эту границу не сдвигает.

```
   человек            Issue-Agent          разработчик          PR-Agent   PR-Closer
      │                    │                    │                   │          │
      │─ задача ──────────▶│                    │                   │          │
      │                    │ валидация          │                   │          │
      │                    │ аналитика          │                   │          │
      │                    │ декомпозиция       │                   │          │
      │                    │ приоритет          │                   │          │
      │                    │─ ready-for-dev ───▶│                   │          │
      │                    │                    │ ПИШЕТ КОД         │          │
      │                    │                    │─ PR ─────────────▶│          │
      │                    │                    │                   │─ ревью ─▶│
      │                    │                    │                   │◀─ фиксы ─│
      │◀─ needs-human:* ───┴────────────────────┴───────────────────┴──────────│
      │                                                                        │
      │◀─ follow-up Issue ─────────────────────────────────────────────────────│
      └────────────────────▶ (обратно в Issue-Agent)
```

Агенты работают **до кода** и **после кода**. Код пишет разработчик — вне контура, своими
инструментами. Агент, пишущий код по задаче, в контуре отсутствует и не планируется.

Это не пробел в архитектуре, а её условие. Смысл контура — довести до качественного результата то,
что написал разработчик, а не заменить его. Правки PR-Closer разработкой не являются: это
минимальный патч в границах уже написанного, под лимитом кругов и тестовым гейтом.

| Владеет контур | Владеет человек |
|---|---|
| Постановка: валидация, аналитика, декомпозиция, приоритет | Техническая реализация и архитектура |
| Обратная связь по PR и доведение до качества | Решение по спорному замечанию |
| Прослеживаемость: задача → ветка → PR → follow-up | Слияние при защищённой ветке |
| Остановка цикла, когда он перестал сходиться | Разбор всего, что помечено `needs-human:*` |

## 2. Среда обмена

GitHub здесь — не транспорт, а **доска объявлений**: агенты пишут состояние, читают состояние
и реагируют на события. Отсюда три следствия, которые нельзя обойти:

1. **Контракт — это словарь меток и соглашение об именах веток, а не API.** Он ломается молча,
   при переименовании метки в одном репозитории. Поэтому словарь версионируется здесь, а не
   дублируется в каждом сервисе.
2. **Общее состояние процесса живёт в GitHub.** У каждого агента свой Temporal-workflow со своим
   состоянием, но ответ на вопрос «где сейчас задача» даёт только GitHub.
3. **Порядок событий не гарантирован.** Вебхук с меткой может прийти раньше комментария, который
   её объясняет. Ни один агент не полагается на порядок — только на чтение актуального состояния
   при старте.

### Почему не прямая шина

Альтернатива — сшить агентов напрямую: общий namespace, parent-child workflow, типизированные
сигналы. Быстрее и строже по типам, но делает процесс невидимым: человек перестаёт видеть, что
происходит, и не может вмешаться руками.

Решение: **GitHub остаётся контрактом**, а машинная сшивка добавляется поверх — общие Temporal
search attributes (§3). Тогда в одном UI централизованного кластера фильтруется вся цепочка
по одной задаче, но человеческий канал остаётся первичным.

## 3. Сквозной ключ

Один идентификатор связывает всё, что порождено задачей: **`root-issue`** — номер исходного Issue.

| Артефакт | Как несёт ключ |
|----------|----------------|
| Ветка | `research/issue-<N>`, `bug/issue-<N>` — соглашение уже действует в Issue-Agent |
| PR | `Closes #N` в теле |
| follow-up Issue | Строка `root-issue: #N` в теле + ссылка на PR |
| Temporal | Search attributes `RootIssue` и `Repo` во всех трёх сервисах |

Search attributes — единственная причина, по которой централизованный Temporal предпочтительнее
трёх изолированных: они дают одну ленту на всю цепочку от триажа Issue до стоп-слова на PR.

Если PR не ссылается на Issue, `root-issue` неизвестен. Это допустимо: PR-Closer работает,
но follow-up вешается на PR, а не на задачу.

## 4. Словарь меток

Правило: **одна метка — один писатель**. Иначе два агента затирают друг друга.

| Метка | Пишет | Читают | Смысл |
|-------|-------|--------|-------|
| `advisor:*` | Issue-Agent | человек | Классификация запроса |
| `priority:*` | Issue-Agent | человек, разработчик | Приоритет по формуле |
| `duplicate`, `possible-duplicate` | Issue-Agent | человек | Подозрение на дубль, решение за человеком |
| `analyzing` | Issue-Agent | — | Идёт тяжёлая стадия анализа |
| `research-me`, `bug-me` | человек | Issue-Agent | Запуск тяжёлой стадии |
| `ready-for-dev` | Issue-Agent | разработчик | **Точка передачи:** задача подготовлена, можно брать в работу |
| `origin:agent` | любой агент | все | Артефакт создан агентом, а не человеком |
| `pr-closer:waiting` | PR-Closer | человек | Ждёт ответа автора PR |
| `pr-closer:ready` | PR-Closer | человек | Готов к слиянию, merge заблокирован защитой ветки |
| `pr-closer:closed` | PR-Closer | PR-Agent, PR-Closer | Работа агентов над этим PR завершена |
| `needs-human:*` | любой агент | человек | Очередь к человеку — единый префикс |
| `agents:off` | человек | все агенты | Рубильник: агенты не трогают этот Issue/PR |

### Унификация очереди к человеку

Сейчас одна и та же сущность называется по-разному: `needs-human-triage` в Issue-Agent,
`pr-closer:needs-human` в спецификации PR-Closer. Приводится к единому префиксу:

| Было | Стало |
|------|-------|
| `needs-human-triage` | `needs-human:triage` |
| `pr-closer:needs-human` | `needs-human:pr` |

Выигрыш прямой: одна выборка по `needs-human:*` показывает всю очередь к людям по организации
и даёт одну цифру для наблюдения.

## 5. Правила контура

**R1. Одна метка — один писатель.** Метку из чужой зоны агент только читает.

**R2. Состояние читается на старте.** Агент не полагается на порядок вебхуков и не хранит
предположений о том, чего не проверил сам.

**R3. Каждая парковка имеет дедлайн.** Ожидание человека без срока превращается в вечную сессию —
ровно ту категорию, ради управления которой брали Temporal. По истечении — `needs-human:*`
и завершение сессии.

**R4. `agents:off` уважается до любой работы.** Проверка выполняется раньше первого обращения
к LLM: смысл в том, чтобы не тратить бюджет на то, что человек уже забрал себе.

**R5. Стоп-метка одного агента уважается остальными.** `pr-closer:closed` останавливает и PR-Agent,
и повторный запуск PR-Closer.

**R6. Провенанс обязателен.** Артефакт, созданный агентом, помечается `origin:agent` и несёт
`root-issue`. Без этого агенты не отличают вход от собственного выхода.

**R7. Потолок глубины.** follow-up, порождённый follow-up-ом, в триаж не идёт — сразу
`needs-human:*`. Иначе контур начинает кормить сам себя: каждый PR рождает Issue, каждый Issue — PR.

**R8. Агент не пишет код по задаче.** Правки PR-Closer ограничены файлами исходного диффа,
лимитом кругов и тестовым гейтом. Это доведение, а не разработка.

## 6. Точки передачи

| # | От | Кому | Токен передачи | Что должно быть верно |
|---|----|------|----------------|------------------------|
| H1 | Issue-Agent | Разработчик | `ready-for-dev` | Классификация, приоритет, дубли проверены; аналитика в ветке `research/issue-<N>`; в комментарии — чеклист готовности |
| H2 | Разработчик | PR-Agent | Открытый PR с `Closes #N` | Ветка от задачи, ссылка на Issue проставлена |
| H3 | PR-Agent | PR-Closer | `pull_request_review` = `changes_requested` | Замечания классифицированы по серьёзности |
| H4 | PR-Closer | Человек | `needs-human:pr` | Указано, что именно не удалось и почему |
| H5 | PR-Closer | Issue-Agent | follow-up Issue | `origin:agent`, `root-issue`, глубина цепочки |

H1 — единственная точка, где контур отдаёт работу человеку по своей инициативе. Её качество
определяет всё остальное: плохо подготовленная задача даёт плохой PR, который агенты не спасут.

---

## 7. Защита контура от самоусиления

Контур замкнут: PR-Closer создаёт Issue, Issue-Agent их триажит. Без защиты бэклог начинает расти
сам из себя.

| Механизм | Правило |
|----------|---------|
| Провенанс | `origin:agent` на всём, что создано агентом (R6) |
| Сокращённый триаж | Issue с `origin:agent` уже классифицирован: только дедуп и приоритет, без advisor-ответа |
| Потолок глубины | follow-up второго уровня — к человеку (R7) |
| Рубильник | `agents:off` — одно действие человека выключает всё (R4) |

---

## 8. Что дорабатывается в репозиториях

Протокол требует изменений во всех трёх сервисах. Координация — в Issue организации.

| Репозиторий | Доработки |
|-------------|-----------|
| poh-issue-agents | Переименование `needs-human-triage`; дедлайн парковки до `research-me`/`bug-me`; метка `ready-for-dev` с чеклистом готовности; сокращённый триаж для `origin:agent`; потолок глубины; `agents:off`; search attributes |
| poh-pr-agents | Классификация замечаний по серьёзности; уважение `pr-closer:closed`; `agents:off`; вывод `root-issue` |
| poh-pr-closer | Переименование `pr-closer:needs-human` → `needs-human:pr`; `origin:agent` и `root-issue` в follow-up; `agents:off` в условиях входа; извлечение `root-issue` из `Closes #N`; search attributes |

---

## 9. Версионирование

Протокол версионируется целиком. Изменение словаря меток или правил — это новая версия
и согласованное изменение во всех сервисах, которых оно касается.

Сервис объявляет поддерживаемую версию протокола в своём `README.md`. Расхождение версий между
сервисами — дефект контура, а не частный баг одного из них.
